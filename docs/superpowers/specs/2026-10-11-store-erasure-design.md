# Nutrition store protection and local erasure design

Status: owner approved the proposed approach on 2026-10-11, retaining the physical-device gate. Implementation and the final protection-class choice remain pending measured device evidence.

This design is the coordinated local-store erasure work for #119, covering the related #228 concern. It keeps one erase flow for the four local stores, states the limits of file removal plainly, and makes the protection policy depend on measurements from a real iOS device. It does not create a competing project or claim secure or forensic deletion.

## Current source facts and evidence limits

`AppServices.make(directory:)` opens four independent SwiftData stores in Application Support: `journal.store`, `favorites.store`, `recipes.store`, and `goals.store` ([AppServices.swift](../../../ios/HealthNutrition/Sources/AppServices.swift)). `SwiftDataJournalStore`, `SwiftDataFavoritesStore`, `SwiftDataRecipeStore`, and `SwiftDataGoalStore` each own an optional `ModelContainer`; their `close()` methods only nil that reference ([journal](../../../ios/NutritionCore/Sources/NutritionJournal/SwiftDataJournalStore.swift), [favorites](../../../ios/NutritionCore/Sources/NutritionJournal/JournalFavorites.swift), [recipes](../../../ios/NutritionCore/Sources/NutritionJournal/SwiftDataRecipeStore.swift), [goals](../../../ios/NutritionCore/Sources/NutritionJournal/SwiftDataGoalStore.swift)). A `ModelContext` already created from a container can retain that container after the wrapper's `close()` returns. Store methods currently create short-lived contexts internally, and the app's store protocols return value types rather than exposing SwiftData models or contexts. Each store currently has an `eraseAll()` row-deletion implementation; the screen invokes the erasers independently, so a failure can leave only some stores erased.

The app graph retains the four store wrappers for its lifetime. `AppServices` also retains view models that cache values from them. `RootView` owns additional recipe navigation/list state and transient add/detail flows. The current erase-generation handler resets recipe routes and add flow and reloads Today, Journal, Library, goals, and the first-day checklist; it does not replace the `AppServices` graph. The current wrappers have no reopen API. Reusing a wrapper after close would require a new API and would let stale clients call into the replacement store unless every operation is bound to a generation. Any lifecycle change must account for the full graph and every route/cache.

`HealthNutritionApp.init()` currently calls `AppServices.make()` immediately, which opens stores before any recovery check. Startup must move store construction behind an async bootstrap controller. Existing app-wide side effects also outlive an individual store call: `ReminderController.setTime()` writes preferences before its queued scheduler work, `syncOnLaunch()` runs at launch and foreground, display-preference setters write synchronously, exports create temporary files, and account tasks can persist a returned session after an await. Store leases alone cannot make erase quiescent.

Imports/restores run on a background executor and already have an `ImportGate` that refuses new imports during erase and waits for in-flight restores ([ConnectionsPrivacyViewModel.swift](../../../ios/NutritionCore/Sources/NutritionUI/ConnectionsPrivacyViewModel.swift)). `RootView` owns additional route and cached model state ([RootView.swift](../../../ios/HealthNutrition/Sources/RootView.swift)). The current source has no `BGTask` registration. HealthKit delivery is only queued in debug builds and is driven by app code ([AppServices.swift](../../../ios/HealthNutrition/Sources/AppServices.swift)); the relay destination is disabled. Future delivery writers must join the same lifecycle gate before they can run. These are source facts, not measurements of locked-device behavior.

No real iOS device measurement is available for this design. The repository's SwiftData configuration specifies store URLs and disables CloudKit; it does not request a file-protection class or establish the attributes SwiftData/iOS applies to the database and sidecars. There is no device evidence here for current protection attributes, WAL/SHM creation or residue, locked reads/writes, open-handle behavior after unlink, or post-erase relaunch. Do not treat defaults inferred from source or simulator output as device evidence.

## Approaches considered

1. **Keep row deletion and apply an explicit protection class.** This is the smallest change and preserves all current container and view-model identities. It does not remove old database pages or guarantee that deleted values disappear from the main file or WAL. It is insufficient for the requested local file removal.
2. **Quiesce all store API calls, close all four old wrappers, remove each store and its SQLite companions, then construct a fresh `AppServices` graph at the same paths.** Old wrappers remain permanently closed, so stale references fail closed. A durable erase record makes restart recovery possible. It removes the app's named database files, but does not promise flash-block sanitization, removal from backups/snapshots, or deletion of copies outside the app.
3. **Write to a fresh generation of four store paths and switch the app graph, then remove the old generation.** This gives a clean namespace switch, but requires path-generation/migration and dependency-graph design, and still cannot revoke a file descriptor or promise forensic deletion of the old generation. It adds complexity without an established need in the current source.

**Recommendation:** approach 2, subject to the device protocol below. Use a new `AppServicesFactory` (or equivalent factory seam) to retain the current directory, reminder scheduler, display-preference dependency, and account-service test seam, close and permanently retire the old wrappers, then construct a wholly new `AppServices` graph after all files are removed. The factory must use the same journal schema/migration plan and preserve `enabledDestinations` exactly: release builds keep `[]`, while debug builds keep `[.healthKit]`. A test/device harness must inject a fake writer so this debug setting cannot cause real HealthKit writes. Swap the root's service graph only after all four new stores open and their selected protection class is verified; destroy old view trees and routes, then load fresh view models. If testing shows a retained context remains usable or any API can outlive its lease, stop and revisit approach 3 before implementation.

## Proposed protection policy, conditional on measurements

The tentative target is `NSFileProtectionComplete` for all four main store files and every SQLite sidecar the app observes. Under this policy, the app must treat a locked-device store operation as unavailable, fail closed, and retry only after protected data is available. The source has no registered background task and release builds queue neither HealthKit nor relay delivery, so there is no source-backed requirement to keep these stores available while locked. SQLite may delete a WAL or SHM file at checkpoint or last close and recreate it on a later write, so verifying only the sidecars present when the candidate graph is built does not cover files created afterwards. The design therefore requires the protection class to be inherited from the store directory (or an equivalent mechanism that applies it whenever a sidecar is created), and the marker may not be declared `clean` until a test has recreated the sidecars after a checkpoint and after a relaunch and confirmed the class on each.

Before implementation, measure normal and erase behavior on the supported physical iPhone and iOS build. If an owner-approved operation must read or write these stores after the first unlock while the device is locked, compare `NSFileProtectionCompleteUntilFirstUserAuthentication` and document the weaker locked-device availability before choosing it. Do not silently weaken the class to make a test pass. `NSFileProtectionCompleteUnlessOpen` is not the recommendation: whether a container or SQLite handle remains open would then affect the protection boundary and erase result. The chosen class must be explicit, applied and verified for the database and companions after creation/recreation, and covered by the device matrix.

The class protects files under the operating system's data-protection model; it is not app-level encryption and is not a claim that previously written flash blocks are overwritten.

## Bootstrap receipt and startup ordering

`HealthNutritionApp.init()` currently calls `AppServices.make()` before the first view is shown. Replace that eager construction with an async `AppStartupCoordinator`: it waits for protected data, validates bootstrap metadata, completes any pending recovery, and only then calls `AppServicesFactory.make()`. The receipt and erase marker are separate records in the app-private support directory: `store-bootstrap.json` is the durable migration-complete receipt; `erase-state.json` is the per-erase intent/progress record. Both use the selected data-protection class and are read only after protected data is available. Neither is a display preference, and `resetToDefaults()` must never clear or recreate them. A successful erase retains both records (`store-bootstrap.json` stays `initialized`; `erase-state.json` returns to `clean`).

The bootstrap receipt contains only a format version, phase (`pending` or `initialized`), mode (`emptyBootstrap`, `preserveLegacy`, or `fullErase`), and an opaque operation identifier. `emptyBootstrap` describes the observed lack of known app state; it does not certify that the app was freshly installed. The receipt is atomically replaced as a sibling file and synchronized before moving to the next step. Startup evaluates receipt/marker state and prior app-owned state before it constructs any SwiftData container or restores an account. The community-session witness is an existence-only Keychain query; it must not restore or publish an account session. Every witness inspection must succeed and positively prove absence before a witness counts as absent: a Keychain status other than success or item-not-found (the session store's load throws for those), or a failed or partial filesystem, defaults, or notification-request enumeration, is an indeterminate witness, never "no witness".

| State observed after protected data is available | Required startup behavior |
| --- | --- |
| Both records absent and no prior-state witness exists (no four store files/sidecars, display-pref keys, the product-sharing pause key, reminder settings/request state, matching app export, or local community-session item) | Treat as an empty uninitialized state, not proof of a fresh install or completed erase. Write receipt `pending/emptyBootstrap`, write marker `clean`, then write receipt `initialized`; only after all three atomic writes succeed may stores/account services be constructed. |
| Both records absent and any prior-state witness inspection fails or is indeterminate | Fail closed: do not treat the failure as absence, do not write a receipt or marker, construct a store, or restore an account, and never enter the empty-bootstrap path. Retry the inspection. While any witness stays indeterminate, classify the state as the ambiguous row below (explicit preservation with an uncertainty disclosure, or a confirmed full local erase). |
| Both records absent but any prior-state witness exists (legacy upgrade or metadata loss) | Ambiguous. Do not auto-bootstrap, open/migrate a store, reset preferences, delete files, or report a clean erase. Offer explicit preservation with an uncertainty disclosure or a confirmed full local erase. On preservation, atomically write receipt `pending/preserveLegacy`, atomically write marker `clean`, validate both records, then mark the receipt `initialized` before normal construction; preserve discovered stores and state. This does not claim a prior erase completed. |
| Receipt `pending/emptyBootstrap` or `pending/preserveLegacy`, marker absent or `clean` | Resume the recorded bootstrap mode idempotently: create/verify the marker `clean`, then atomically mark receipt `initialized`. For preserve mode, do not erase or reset prior data. Before any discovered store is opened, apply the selected protection class to every canonical existing store file and SQLite companion with a per-file `fileProtectionKey` (a directory class does not migrate files that already exist), verify it, and fail closed without marking the receipt `initialized` or constructing the graph if any file cannot be migrated. |
| Receipt `pending/emptyBootstrap` or `pending/preserveLegacy` with a valid marker `erasing`, `recreating`, or `recoveryRequired`, or with a marker that is corrupt, unsupported, or unreadable after protected data is available | Inconsistent records: the receipt does not confirm an erase, and the marker contradicts the bootstrap. Fail closed before normal service construction/account restore. Do not resume the marker's erase from these records, do not complete the bootstrap, and do not offer preservation or normal startup. Offer only a confirmed full local erase, which first atomically writes receipt `pending/fullErase` and a matching `erasing` marker before any cleanup. |
| Receipt `pending/fullErase`, marker absent, `clean`, `erasing`, `recreating`, or `recoveryRequired`, or marker corrupt, unsupported, or unreadable after protected data is available | The valid pending receipt retains the confirmation and operation identifier, so no new confirmation is needed. A valid in-progress marker carrying the receipt's operation identifier keeps its completion flags. In every other case (absent, `clean`, corrupt, unsupported, unreadable, or a different operation identifier) atomically write a new `erasing` marker with the receipt operation identifier and every completion flag false before cleanup, so the idempotent components all run again. Recover the full erase, then use the restricted candidate-graph step below. Do not expose a normal service graph or restore an account until both records are valid and complete. |
| Receipt `initialized` plus valid marker `clean` | Normal startup may proceed after protected data is available. |
| Receipt `initialized` with valid marker `erasing`, `recreating`, or `recoveryRequired` | Fail closed before normal service construction/account restore and resume the already-recorded erase through restricted recovery. Never call this a new first launch. |
| Receipt `initialized` with marker missing, corrupt, unsupported, unreadable after protected data is available, or otherwise not valid `clean`/in-progress state | Fail closed before normal service construction/account restore. Offer only a confirmed full local erase recovery; do not offer preservation or normal startup. Never call this a new first launch. |
| Receipt absent and valid marker `clean` | Do not construct stores or restore an account yet. Offer explicit preservation with an uncertainty disclosure or confirmed full local erase. Preservation atomically writes receipt `pending/preserveLegacy`, validates the existing `clean` marker and new receipt, then marks receipt `initialized` before normal construction; it makes no claim that a prior erase completed. |
| Receipt absent with marker `erasing`, `recreating`, or `recoveryRequired`, or marker corrupt/unsupported/unreadable; malformed/unsupported receipt | Fail closed with no normal construction and no preservation branch. A valid in-progress marker may resume its recorded erase; otherwise require confirmation of a full local erase. |
For a newly selected empty-bootstrap or preserve mode, ordering is: atomically write `store-bootstrap.json` as `pending/<mode>`; atomically write or validate `erase-state.json` as `clean`; validate both records; in preserve mode only, apply the selected protection class with a per-file `fileProtectionKey` to every canonical existing store file and SQLite companion, verify it, and fail closed (receipt stays `pending`, no graph) if any file cannot be migrated, the same rule the resume path applies; atomically mark the bootstrap receipt `initialized`; then construct the normal app graph. For a full-erase mode, write the pending receipt, then the matching `erasing` marker, execute all components, and move the marker to `recreating` before constructing an isolated candidate graph. The candidate opens only the four empty stores under the recovery coordinator; the root remains blocked, no account is restored, no delivery is enabled, and no user operation is admitted. Verify empty reads and file protection, persist `newGraphAndProtectionVerified`, atomically mark the erase record `clean`, then atomically mark every `pending/fullErase` receipt `initialized`, whichever path wrote it (a legacy bootstrap erase, or a confirmed recovery erase that replaced an `initialized` receipt), and only then expose/swap the graph and reopen admission. The graph is never exposed while the receipt is still `pending`: a crash between the clean marker and the initialized receipt re-runs the full erase on next launch over stores no user operation has reached, so no newly entered data can be erased by a stale pending receipt. If candidate construction fails or is interrupted, keep recovery active; discard any candidate wrappers and retry candidate construction only after confirming/removing files created by that attempt at the four exact paths. No personal old store remains at that phase because each old-store component was already durably completed. A crash at each step resumes from the last durable record. The receipt is retained across erases and display reset. If either atomic write fails, no normal app graph opens. Bootstrap initialization never silently deletes legacy data to make migration succeed. The empty-state case and total loss of both records can be observationally identical when no prior-state witness remains; initialization may create a new empty state, but must record only that observed fact and cannot claim the app was freshly installed or that a prior erase was proven complete.

When both metadata records are missing but old files/state remain, neither their age nor their presence proves that no erase was interrupted. Explicit preservation requires writing and validating a pending preserve receipt and clean marker before normal construction; otherwise use a confirmed full local erase. If both records and all app-owned witnesses are gone, there is no local signal from which software can recover that history; this is a detection limit, not evidence of a completed erase.

## Erase lifecycle

Implement one app-wide `AppOperationGate`, owned with the service-graph controller, with states `ready`, `erasing`, and `recoveryRequired`. A lease covers every side effect from entry until all synchronous/asynchronous continuations finish: every store API/context lifetime (read and write), import/export, active export-share presentation/file readers, reminder scheduling and settings, display-preference mutation, account/session operation, HealthKit delivery, and any future relay/outbox work. Store readers hold a read lease for the entire context lifetime, then release the context before releasing the lease. This includes counts, existence checks, main-actor calls, and background-executor reads; audit every context creation site and make an unleased path impossible. Import restore must acquire its lease before reading store state and hold it through commit. Export holds its lease through file creation, publication of its URL/state, share-sheet dismissal or completion, and cleanup on failure. `ReminderController` must acquire before `setTime()` mutates preferences, and launch/foreground `syncOnLaunch()` must be admitted through the same gate. All display-preference setters and all account operations acquire a lease before their first mutation/request and retain a generation token across awaits; a result from an invalidated generation cannot write preferences, Keychain, schedule a notification, publish a URL, or change the replacement graph. Gate closure disables UI admission, cancels queued-not-started actions, dismisses/invalidates export sharing, invalidates the old generation, and waits for every active lease—including synchronous and background readers—to drain. Any active system scheduler operation must finish before its lease releases; if it cannot finish before the bounded timeout, refuse erase before cleanup. No old continuation may run a new side effect after cleanup has passed its drain point. The eraser receives a private exclusive token to perform its own cleanup writes while public leases are closed. A timeout refuses erasure before any store or other local file is touched.

Once quiescent:

1. Before the first store or account restore on every launch, wait until protected data is available. The marker and stores use the selected class; when that class makes them unavailable while locked, do not try to decode the marker, construct a container, or restore the Keychain session until iOS reports protected data available.
2. Persist the versioned erase-intent record described below before closing stores. It contains only an operation identifier, state, generation, and component completion flags, never personal store contents. Every new erase is a whole new record, not a phase change on the retained one: the same atomic write that sets `erasing` assigns a new operation identifier and generation and sets every component flag and `newGraphAndProtectionVerified` to false. The retained `clean` record has those flags true from the previous erase, so carrying its payload forward would let cleanup be skipped; a record in `erasing` whose flags were not reset for its operation identifier is invalid and is handled as a corrupt marker. Keep the marker present in `clean` state during normal operation; startup may not equate a missing marker with a clean state.
3. Run exactly one local account cleanup operation, the PR-06 `discardLocalSession()` backed by Keychain removal, while session restoration and account actions remain gated. That cleanup must not depend on an account client: when `CommunityClient.make()` fails (an unsigned or self-built app, or invalid project settings) there is no `AccountViewModel` and the account erase closure returns without deleting anything, so the coordinator needs an unconditional seam backed directly by `KeychainCommunitySessionStore.clear()`. Record `keychain` complete only after that clear succeeds or the item is confirmed absent. The coordinator owns this step; do not invoke a second Keychain discard from the screen or another eraser. Record its `keychain` completion once it succeeds. Never call server logout, account deletion, or shared-label retraction. A Keychain error remains incomplete; do not show success or allow automatic session restoration while that component is pending.
4. Close admission to every read and write lease, wait for every context/API lease to end, then permanently retire all four wrappers. Do not expose containers or contexts outside the wrappers. An active context retains its container after the current `close()` merely nils the wrapper property, so no file may be removed until all context leases have drained.
5. For each canonical store path, attempt removal of the main database and the exact SQLite companion paths for that store: `<store>-wal`, `<store>-shm`, and a present `<store>-journal` rollback journal. Never glob beyond those per-store siblings or sweep unrelated files/the whole Application Support directory. Attempt every store even if one path fails, and persist per-store completion so relaunch can safely retry idempotently.
6. Run every remaining component in the existing erase scope under the same durable state: cancel/remove the daily reminder and clear its stored switch/time (`ReminderEraser`). The system calls that remove pending and delivered notification requests return immediately and complete asynchronously, so `cancelDaily()` returning is not proof of removal: the cancellation must await the notification center, then re-read both the pending and the delivered requests for the reminder identifier and confirm neither remains, and only then record `reminder` complete (a failed or unverifiable read leaves it incomplete and recovery retries it on relaunch); remove every app-owned export matching the exporter's exact `journal-export-<timestamp>.json` name pattern in this app's `FileManager.temporaryDirectory` (do not delete unrelated temporary files); remove all display-prefixed defaults keys and the account-linked `community.productSharing.lifecyclePauses` default (written by `AppServices` before an account erase and not covered by `resetToDefaults()`, so it is its own durable cleanup component, `productSharingPause`, and a prior-state witness); and reset the export URL/export screen state to idle. The Keychain session is handled only by step 3. Re-enumerate the scoped temporary directory on recovery so exports created before the erase began or left by interruption are retried. Persist completion per component; do not declare completion while any required item fails.
7. If any required store file or other component remains, retain the marker, keep the service graph unavailable (and account restore gated), show incomplete erase with retry/relaunch guidance, and do not construct a mixed graph. On next launch, retry incomplete components before opening stores or restoring the account. Do not claim successful erase until every required component has completed.
8. Once component cleanup is complete, persist marker phase `recreating`. Construct four fresh wrappers through `AppServicesFactory` as a restricted candidate graph; keep app operations, account restore and delivery disabled. Verify all four stores are empty and the selected protection class is present on every created main file/sidecar. If construction or verification fails, close/retire the candidate wrappers, mark recovery required, and retry only after safely removing candidate files from the four exact paths. Never silently open a default-protection store. Persist `newGraphAndProtectionVerified`, then atomically write marker state `clean` only after every component and candidate graph succeeds. Whenever the bootstrap receipt is `pending/fullErase`, including a recovery erase of a previously initialized installation, atomically mark it `initialized` as well and validate it before the swap; if that write fails, keep recovery active and do not expose the graph. Then atomically swap the root to the new `AppServices` graph, invalidate the old root/view tree and async generation, and reopen operation admission. A crash after the clean marker and initialized receipt but before the root swap is safe: next launch constructs the clean graph before exposing app operations.
9. Reload through the new graph and clear view state: close selected entry detail and all recipe/add/edit routes; clear held selections/copies and export URL; load Today, Journal, Library/favorites, recipes, Goals, first-day checklist, Connections/privacy, reminder state, account view, and debug delivery status. Debug delivery status and the delivery worker must use the new journal wrapper. No stale screen or callback may mutate the new generation.

The old wrappers are never reopened. `closeAndDrain()` is the required new wrapper lifecycle seam: it closes lease admission, waits for all context and API leases to end, then nils the wrapper's container and permanently marks that wrapper generation retired. `AppServicesFactory.make()` constructs new wrapper instances and a new graph; it preserves the canonical directory, schemas, journal migration plan, and release/debug `enabledDestinations` described above. All old view models retain only retired wrappers, so any late call fails closed. The root/service controller replaces the full graph and creates fresh `TodayViewModel`, `JournalViewModel`, `LibraryViewModel`, `GoalsViewModel`, `FirstDayChecklistModel`, `ConnectionsPrivacyViewModel`, `RecipeListViewModel`, account, reminder, and delivery objects. All asynchronous work carries a generation token; a result from a retired token is dropped before any state or store write. The implementation must audit all store API calls and context creation sites when a new consumer is added.

`ModelContainer` does not provide an app-facing close operation in this source. Dropping the wrapper's reference is the available lifecycle seam; it is not by itself proof that SwiftData has released every underlying descriptor. Device testing must exercise retained wrapper/context scenarios and file residue. The design does not use SQLite `PRAGMA`, raw SQLite writes, `VACUUM`, or undocumented manipulation behind SwiftData.

## Partial failure and recovery semantics

There is no cross-file transaction across four independent stores, the Keychain, preferences, reminders, exports, and the marker. The durable intent record is the recovery boundary, not a promise of all-or-nothing physical deletion. Store and component operations must be idempotent and have separate completion flags: `keychain`, each of four store main+sidecar sets, `exports`, `reminder`, and `exportViewStateReset`; the display-preference and product-sharing-pause components have no flag in the marker file at all, only the defaults-domain token described below. The export view state is cleared before writing its completion flag; if the process stops, the destroyed view tree makes that reset naturally repeatable. Report failure if any required item, container creation, or protection verification fails. Attempt independent erasers even after one failure, but do not publish a new service graph or reopen access while any required item is incomplete. On launch, recover the record before account restoration or any store access. Retrying completed removals and a completed local-session discard is idempotent.

**Preference completion is durable only with the removal itself.** `UserDefaults` applies a removal in memory at once and writes the domain to disk asynchronously, and there is no public acknowledgement that the write finished. So there is no marker-file flag for `displayPreferences` or `productSharingPause`. A single completion token is stored in the same defaults domain as the values it vouches for, bound to the current erase `operationID` (a token from an earlier operation never counts), and written after the removals: the domain is persisted as one unit, so a terminated process leaves either the removals and the flag together or neither. Recovery treats an absent flag as "run the removal again" (it is idempotent), and the marker may transition to `clean` only after a read of the persisted domain shows every owned key absent and a token matching the current `operationID` present. A marker that says `clean` without a matching token and absent keys in the defaults domain is treated as incomplete, not as success.

If the process is killed at any point after intent is durable, launch recovery repeats unfinished steps before normal service construction. Store the record as `<Application Support>/HealthNutrition/erase-state.json`, in the same app-private directory as the four stores. The separate bootstrap receipt is `<Application Support>/HealthNutrition/store-bootstrap.json`; validate both before `HealthNutritionApp` may construct stores. Use a versioned JSON erase record with `formatVersion`, opaque `operationID`, monotonic `serviceGeneration`, `phase` (`clean`, `erasing`, `recreating`, or `recoveryRequired`), and completion booleans for `keychain`, `journalStoreFiles`, `favoritesStoreFiles`, `recipeStoreFiles`, `goalsStoreFiles`, `exports`, `reminder`, `exportViewStateReset`, and `newGraphAndProtectionVerified`. The marker has no `displayPreferences` or `productSharingPause` field, so no implementation can mark those components complete from the marker file. The component names are fixed local enums, not user data. The record also carries `origin` (`bootstrap` or `erase`), and clean-record validation is origin-specific. An `erase`-origin record is `clean` only when every one of these booleans is true, including `productSharingPause` and `newGraphAndProtectionVerified`, and validation rejects a record that omits one. A `bootstrap`-origin `clean` record is the one written by the empty-bootstrap and preserve paths before any graph exists: it asserts only that no erase is in progress, every completion boolean in it is false, it makes no graph-verification claim, and validation rejects a bootstrap-origin record with any flag true or any phase other than `clean`. Every erase writes an `erase`-origin record with a new operation identifier and all flags false before cleanup. Update it by writing a sibling temporary file, applying the marker's selected protection class, synchronizing the file, and atomically replacing the prior record; never truncate the only valid copy in place. Persist progress after each idempotent component. If any component fails, atomically set `phase` to `recoveryRequired` while preserving its incomplete flag; if this state update fails, leave the last valid non-clean record and still fail closed. After an initialized receipt, any missing, unreadable, malformed, unsupported, unknown, or non-clean marker other than a valid recorded in-progress erase permits only confirmed full local erase recovery—never normal startup or preservation. With no receipt, a valid `clean` marker permits only the explicit uncertainty-preservation flow (which writes a pending receipt and validates both records before construction) or confirmed full erase; an in-progress marker may resume its recorded erase, while corrupt/unknown metadata permits only confirmed full erase. The restricted recovery coordinator may create an isolated candidate graph only in `recreating`, with all app operations and account/delivery flows gated; it records graph verification before marking clean. A confirmed retry must first atomically write a valid pending full-erase receipt and matching `erasing` record; if either write fails, do not delete anything. Do not infer `clean` from absence, partial file presence, or source defaults. A failed intent write means do not start the erase. A failed erasure is never described as complete.

## Synthetic physical-device measurement protocol

Run this only on a designated physical iPhone with a debug/test build and synthetic records that contain unmistakable fake tokens, never personal data. Use an injected no-op HealthKit writer and fake relay transport for every harness run; do not invoke `HealthKitSampleWriter`, save samples to Apple Health, or contact a relay/server. Current debug `AppServices` wires the real HealthKit writer, and `RootView` may trigger delivery after journal changes, so the harness must override both the writer and delivery trigger before creating the test graph. No actual HealthKit write is authorized by this protocol; it needs separate explicit owner authorization on an isolated test device. Record the app build, iOS version, device model identifier, selected protection class requested, and test run identifier. Redact device identifiers from any public artifact; keep only the attributes needed to reproduce the run. A simulator can help develop the harness but cannot satisfy this protocol.

1. Start from a clean test installation. Write one synthetic sentinel to each store: a journal entry, favorite, recipe, and goal. Add enough journal writes to cause SQLite sidecar creation. Record, per canonical store path, existence, file size, file-protection attribute requested and observed, and whether main database, `-wal`, `-shm`, or rollback-journal files exist. Capture the attributes after writes, after app backgrounding, and after relaunch; do not infer a sidecar attribute from the main database attribute.
2. With the app foregrounded, lock the device and attempt only the approved synthetic read/write probes through the app's stores. Record success or the exact protection error for each store. Repeat after first unlock and after a subsequent lock. Separately test an in-flight synthetic import and fake/no-op delivery operation when locking begins; verify the lifecycle gate drains or refuses it and cannot create a post-erase write. Keep account restoration gated until protected data and the marker are readable.
3. Retain references to the old store wrappers and any test-created context that the harness can retain without adding production escape hatches. Begin erase while synthetic writes are queued/running. Verify that admission closes, old operations drain or time out before deletion, stale references cannot read sentinel rows or write after erase, and no callback repopulates any store.
4. After erase completes, enumerate each exact main/sidecar path and record which remain. Verify the four recreated stores are empty through normal app reads, then terminate and relaunch and verify they remain empty. Create one new synthetic row per store after erase and verify each persists across another relaunch. Record protection attributes for every recreated file and sidecar.
5. Inject a deterministic file-removal failure for one path. Verify the user sees incomplete erase, all other paths are attempted, no container opens over a mixed old/new set, the durable marker survives termination, and retry/relaunch completes before normal access. Separately inject Keychain cleanup failure and verify there is no success result and session restoration remains blocked.
6. Save a concise run record with pass/fail and raw measured attributes/residue for every store. These are the only evidence that can establish device behavior. If the device or harness is unavailable, mark every device result unknown and leave class choice and implementation approval pending.

The device protocol can demonstrate which app-visible files remain and whether this app can read/write through tested handles. It cannot prove that NAND flash cells, filesystem snapshots, system backups, crash dumps, or recipient copies have been physically purged.

## Validation matrix for implementation approval

| Scenario | Required result |
| --- | --- |
| Device files after normal writes and after erase | Actual protection attributes recorded separately for all four stores and every observed sidecar; after successful erase the named store paths and companions are absent before fresh containers are created. |
| Retained old references | Old wrapper references fail closed after retirement. A harness-retained context/reader cannot read sentinel data or write/repopulate after deletion; in-flight read/write/API leases either drain before deletion or cause erase to refuse before touching files. If SwiftData keeps a retained context usable after deletion, approach 2 is not approved for implementation. |
| Relaunch | Successful erase relaunches with all four stores empty; interrupted/partial erase recovers from the durable marker before normal store APIs or account restore run. Only the restricted candidate graph in `recreating` may open the four stores while user operations/account/delivery remain gated. |
| Post-erase writes | New synthetic journal, favorite, recipe, and goal writes succeed and persist after relaunch under the same selected protection policy. |
| File deletion failure | All independent path removals are attempted; result is incomplete, no mixed stores reopen, and retry after termination finishes recovery before app access. |
| Full existing erase scope | Every store, exact-pattern app export in scoped temporary directory, display-prefixed default, the account-linked product-sharing pause default (`productSharingPause`: removed, vouched for by the operation-bound defaults-domain token, and retried on relaunch after an interruption), reminder request/setting, Keychain session, and in-memory export state is erased or explicitly listed incomplete; relaunch retries incomplete components before store/account access. |
| Bootstrap/upgrade/recovery states | Observed empty-state bootstrap, legacy state without records, pending bootstrap, initialized plus missing marker, and either missing record are classified before store construction. Legacy state is never silently deleted or called a clean migration; loss of both metadata files with no remaining witness is reported as undetectable history. |
| Witness inspection failure | A Keychain status other than success or item-not-found, or a failed filesystem, defaults, or notification enumeration, with both records absent blocks empty bootstrap; no receipt, marker, store, or account restore results, and the state is offered only preservation with uncertainty or a confirmed full erase. |
| Recovery erase of an initialized installation | After a missing or corrupt marker forces a confirmed full erase, the receipt is `initialized` before the fresh graph is exposed; synthetic data written afterwards survives relaunch and is not erased again. A crash between the clean marker and the initialized receipt re-runs the erase before any user operation is admitted. |
| New erase over a retained clean marker | Starting an erase after an earlier completed erase writes a new operation identifier with every completion flag false; a fixture that keeps the old true flags is rejected as corrupt, and no component is skipped. |
| Pending full erase with a corrupt marker | A `pending/fullErase` receipt with a corrupt, unsupported, or unreadable marker resumes without a new confirmation from a fresh all-false `erasing` record and completes. |
| Bootstrap marker schema | The `clean` marker written by empty bootstrap or preservation validates as bootstrap-origin with all flags false; it is never read as proof that a graph was verified. |
| Marker failure/corruption | Atomic marker replacement preserves the last valid record. Missing after bootstrap, unreadable after protected data is available, malformed, or unknown-version state blocks store creation and account restore; recovery requires a confirmed full local erase retry. |
| Keychain failure | Result is incomplete; other safe local erasers still run; account identity/session restoration and account writes remain blocked until local session discard succeeds. |
| Locked behavior | The selected class matches measured foreground/background requirements. Under `Complete`, operations fail closed while protected data is unavailable and recover after unlock; any alternate class has an explicitly approved and measured locked-state contract. |
| Non-store operations in flight | A synthetic export/share, reminder time change, launch/foreground sync, display-preference mutation, or account operation is admitted before erase and held/drained or canceled with a generation guard. No old continuation recreates an export, rewrites preferences, reschedules a notification, or persists a session after cleanup; a drain timeout refuses before cleanup. |
| Stale async work | An import completion, delivery acknowledgement, view-model task, or old account response cannot recreate data or mutate a replacement container after erase; every synchronous/background read and write context stayed within a generation-bound lease. |
| Delivery isolation | Device tests use fake/no-op writer and transport, with automatic delivery trigger disabled; no HealthKit sample is saved and no relay/server is contacted. |

## User-facing claim boundary

Copy may say the app closes and removes its four local store files and SQLite companions, then creates empty stores again, if the implementation and device matrix verify that behavior. It must say that deletion is not guaranteed to overwrite prior flash blocks and does not remove system backups/snapshots or copies already exported, shared, delivered to Apple Health, a relay, or a server. It must not say “securely erased,” “forensically erased,” or that `VACUUM` makes erased data unrecoverable. Existing public copy remains unchanged until behavior is implemented, measured, and reviewed.

## Decisions required before implementation

- Review and approve approach 2 or select another approach after the physical-device evidence is available.
- Choose `NSFileProtectionComplete` if measured app flows can fail closed while locked; approve `NSFileProtectionCompleteUntilFirstUserAuthentication` only if a demonstrated, owner-approved background requirement needs it.
- Approve the durable erase-intent/recovery state and restricted failure behavior, including the Keychain retry gate from PR-06.
- Approve the exact user-facing wording after the implementation and device measurements establish what files are removed.

Until those decisions and measurements are reviewed, this document is a design proposal only. No implementation, test claim, or changed erase guarantee is authorized by it.
