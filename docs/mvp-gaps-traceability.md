# MVP-GAPS traceability: remaining daily-workflow requirements

A requirements traceability check of the ten daily-workflow requirement areas, recorded against the code at
`3bfbee7`. Each area gets one verdict, the `file:symbol` that carries it, the test that would fail if it broke, and
the gap. Rows 3 and 5 were re-recorded when the entry-time correction and the meal labels were built; every other row
is still the reading taken at `3bfbee7`.

The bar used here: **a screen existing is not a behaviour being implemented.** A fixture, a DTO, a column, a view
that renders placeholder text, or a passing schema test is not implementation. "Implemented" means a real code path
plus a test that would fail if that path broke.

Verdicts are exactly the four in the brief — *implemented*, *partial*, *scaffold*, *unverified* — so results stay
comparable by value. One area (4) has **no code of any kind** behind it, not even a type or a fixture, which those four
values do not describe exactly. That row carries the plain value *unverified* and its gap column opens with **Confirmed
absent** to record the stronger fact: the absence was established by exhaustive search rather than merely failing to be
established. Read the gap column, not the verdict alone, for row 4.

Every path below is **relative to the repository root**. A line number is a hint, not a stable anchor: a row that was
re-recorded names a line from the code as it stood when it was written, the rest from `3bfbee7`.

- **Partial:** 1, 2, 3, 5, 6, 7, 8, 9, 10.

- **Unverified:** 4 — its absence was positively established by exhaustive search rather than merely failing to be

## Notes on the evidence

Two things a reader should know when re-running this check.

- Absence was established by exhaustive search, not by sampling: `remind` and `notif` return zero matches across `ios/NutritionCore/Sources` and `ios/HealthNutrition/Sources`. The tokens
  `goal`, `AppStorage` and `UserDefaults` used to be on that list and have been dropped from it: goals (area 1) and the display
  preferences (areas 2 and 6) ship now, so those tokens are expected in production sources and can no longer be evidence of
  anything's absence. The only occurrences of a `Settings.swift` (no such file exists) in the repository are synthetic fixtures inside
  `scripts/tests/test_check_privacy_manifest.py:159`, which assert that such code would *fail* CI.
- `AppStorage` and `UserDefaults` are no longer asserted absent: the unit preference and quick-water
  preference are stored through `UserDefaults` at
  `ios/NutritionCore/Sources/NutritionUI/DisplayPreferences.swift`, which is declared in
  `ios/HealthNutrition/Resources/PrivacyInfo.xcprivacy` with reason `CA92.1`. `@AppStorage` is still absent
  from every production source; the preference is read through a plain protocol so the app controls when
  values are read.
- "The model can store it" and "the user can see it" are different guarantees, and the areas above separate them
  deliberately. Areas 3, 8 and 9 all persist or model the data and none of the three surfaces it.
