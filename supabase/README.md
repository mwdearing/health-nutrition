# Supabase backend

Community label catalog (see `migrations/`). Signed-in accounts with sharing on can submit nutrient labels. An eligible community aggregate can be shown after two accounts agree within 2 percent; it is always unverified, regardless of how many accounts agree. The newest 100 submissions bound only the community aggregate calculation. The repository includes a forward owner-verification migration and tests; this README does not indicate whether that migration has been applied to a hosted project.

- Community candidates, owner-approved snapshots, rejections, and the append-only moderation audit live in private `catalog` tables with row-level security and no app-role table access. An approved snapshot is an independent, bounded payload with no contributor or submission link; later withdrawal or account deletion does not remove it.
- `submit_label` and the legacy `lookup_label` remain available to signed-in accounts only; anonymous sign-ins are refused. Submission results are `received` or `shared`, never verified by community agreement.
- `lookup_label_v2` returns an active owner-reviewed snapshot first with source `owner_reviewed`, `verified=true`, and `supporting_devices=0`; otherwise it can return an eligible community row as `community`, `verified=false`. Rejection suppresses both sources. The legacy lookup keeps its old response shape, returns community rows only, and suppresses a key while an owner-approved snapshot is active.
- Moderation is an explicit project-owner action through the owner-only SQL functions (`catalog.owner_approve_label`, `owner_reject_label`, `owner_clear_rejection`, `owner_revoke_label`). App roles cannot invoke them or access the approval and audit tables. Every action is recorded in the append-only audit. Rejection hides both sources; clearing rejection may reveal only an eligible unverified community row; revocation removes the active snapshot and may fall back to an unverified community row.
- Tunables are one row in `catalog.settings`: `min_shown` (2), `tolerance_percent` (2), `daily_limit` (60). The retained `min_devices` value (5) is legacy compatibility state, not a verification threshold.
- Test: `supabase/tests/run.sh` (needs podman or docker).

## Configuration
The checked-in `config.toml` records the repository's intended Auth values: anonymous sign-ins off (`auth.enable_anonymous_sign_ins`), email confirmation on and six-digit OTPs (`auth.email.enable_confirmations` and `auth.email.otp_length`), and Apple enabled (`auth.external.apple.enabled`). See Supabase's [local-development config reference](https://supabase.com/docs/guides/local-development/cli/config) for the file's scope. The Apple client ID and secret are environment references, not committed values. These fields are intended to stay aligned with the hosted project, but the file and its tests only describe repository state; they do not prove the current hosted settings.

The app's email sign-in flow expects a one-time code: it requests an email OTP and verifies the submitted code. The six-digit setting controls the code length; the hosted [Magic Link email template](https://supabase.com/docs/guides/auth/auth-email-passwordless#with-otp) must include `{{ .Token }}` to deliver a code instead of a link. The commented `[auth.captcha]` example in the Auth section is ignored by TOML and does not prove that hosted CAPTCHA enforcement is enabled or disabled. Verify that separately in read-only hosted evidence.

The checked-in database network-restriction and SSL sections are also not evidence of hosted posture. In particular, `[db.network_restrictions]` describes values in this file, while `[db.ssl_enforcement]` is commented out. The hosted network allowlist, database TLS enforcement, and hosted password-policy settings remain unknown until independently verified from a sanitized, read-only hosted settings view. Missing or unverifiable fields are unknown, not compliant. This repository change does not resolve those open checks.

`supabase config push` applies the local file to the linked project immediately ([CLI reference](https://supabase.com/docs/reference/cli/supabase-config-push)). It is a live configuration change, not a preview or dry run; never use it to inspect or preview hosted settings. Review the full config and obtain separate approval before any push.

## Shared products v2 migration order

Apply the owner-verification migration before the shared-products base, legacy bridge, publish-resolution and bounded-publication migrations, in filename order. The bridge wraps the installed owner helpers and legacy RPCs with shared identity/product locks. Installing owner SQL after those wrappers is not a supported upgrade path. Historical v2 migrations remain unchanged.

`bash supabase/tests/run.sh` checks fresh installation, legacy and v2 behavior, actual blocked-session races, and owner upgrade from seeded legacy consensus rows through the active wrappers. `CATALOG_TEST_SEEDED=1 bash supabase/tests/run.sh` also seeds the legacy/v2 bridge boundary. `CATALOG_TEST_FOCUS=upgrade` runs the owner upgrade checks alone. The stale-writer race uses a test-only scheduling barrier in the old function and a negative control without the invariant; the exact migration must reject that old verified write.

The capability gate closes new v2 publications while retaining receipt replay, resolution, withdrawal, reads and legacy RPCs. It is not an instantaneous drain of in-flight writes. Retain additive tables and evidence during rollback. Deployment requires a separately reviewed artifact, metadata backup and authorization; this source tree makes no claim of hosted application.


The final additive migration advertises `bounded_publication_version:1` and adds authenticated read-only `get_catalog_product_alternatives_v2`. Bounded publication embeddings preserve complete support/review evidence and expose explicit alternative totals/cursors. All detail/mutation/recovery wrappers and alternatives pages fit 262144 serialized bytes; search fits 786432. See the [contract proof](../contracts/catalog-api/shared-products-v2.md#bounded-publications-and-complete-alternatives). The runner includes large valid multi-account sets and table-valid historical raw-name fixtures; these fixtures are invented local state, not observed hosted records. Only the bounded v2 legacy display name may omit outer ASCII spaces with explicit metadata; standalone legacy lookup payloads and historical migration bytes remain unchanged.
